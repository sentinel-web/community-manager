# Server APIs (custom methods & publications)

The hand-written Meteor methods and publications in `server/apis/` that go **beyond** the generic CRUD factory — aggregations, cross-collection enrichment, RSVP/attendance, backup/restore, demo-data seeding, FK-integrity tooling, and field-availability validators. The generic `.read/.insert/.update/.delete/.count/.options` methods are generated by `server/crud.lib.ts` and are **not** documented here; this doc covers the bespoke surface only.

## Key files

- `server/apis/attendances.server.ts` — `attendances.upsert`: atomic per-event attendance grid write under a dynamic `[memberId]` key.
- `server/apis/backup.server.ts` — full-DB export / restore / validate, with SEC-004 privilege-escalation hardening and DDP rate limits.
- `server/apis/dashboard.server.ts` — role-gated dashboard aggregations (counts + group-by via raw Mongo `aggregate`).
- `server/apis/demoData.server.ts` — dev-only `demoData.generate`: wipe-all + reseed every collection from fixed `_id` seeds.
- `server/apis/events.server.ts` — `events` publication (private-event scoping), `events.rsvp`, `events.detail` (enriched single event).
- `server/apis/integrity.server.ts` — FK-graph preview / scan / one-off orphan-resolution methods (admin-only).
- `server/apis/logs.server.ts` — audit-log read/insert/remove/count + `logs` publication; exports `createLog()` used everywhere.
- `server/apis/members.server.ts` — the largest custom API: scoped member read/insert/update/remove (custom mutation paths), option lists, `profileStats`, `attendanceBreakdown`, name/id validators.
- `server/apis/orbat.server.ts` — `orbat.squads` (tree source) and `orbat.popover.items` (per-squad member roster).
- `server/apis/palette.server.ts` — `palette.search`: permission-filtered multi-collection regex search for the Cmd+K palette.
- `server/apis/questionnaireResponses.server.ts` — response submit/validate/list/revoke/ignore; exports `canUserRespond()` + interval helpers.
- `server/apis/questionnaires.server.ts` — `questionnaires.getActiveForUser`: active questionnaires enriched with the caller's response eligibility.
- `server/apis/registrations.server.ts` — `registrations.validateId` / `validateName`: cross-collection (members + registrations) uniqueness checks.
- `server/apis/settings.server.ts` — `settings.public` / `settings` publications + key/value upsert/remove/findOne.
- `server/apis/specializations.server.ts` — `specializations.names` (id→name join) and `specializations.request` (audit-only request).
- `server/apis/squads.server.ts` — `squads.members`: per-squad member summary (rank + position resolved).
- `server/apis/tasks.server.ts` — `tasks.addComment`: append a comment to a task.

## How it works

### Registration & file conventions

Each `server/apis/<feature>.server.ts` body is guarded by `if (Meteor.isServer)` and calls `Meteor.methods({...})` and/or `Meteor.publish(...)`. **A file only registers if it is imported in `server/main.ts`** — all 17 files are imported there (`server/main.ts:11-27`) in alphabetical order. Conventions enforced across the directory:

- **One API per file** — `squads.*` lives in `squads.server.ts`, never scattered.
- **Alphabetical ordering** of files (imports) and of entries inside collection-spanning arrays.
- Methods are `async`, use `*Async` collection methods, validate inputs with the `validate*` helpers from `server/main.ts`, gate on `checkPermission`, and emit audit entries via `createLog` (re-exported from `logs.server.ts`).

### Two mutation styles

Custom methods split into two camps depending on whether they need the full audit lifecycle:

| Style | Used by | Mechanics |
|-------|---------|-----------|
| **Pipeline** (`runMutation`) | `members.{insert,update,remove}`, all of `integrity.*` | Routes through the shared `MutationWithAudit` lifecycle (auth → permission → validate → body → audit), so a denial emits `<collection>.<op>.denied` automatically. See `server/mutation-pipeline.ts` and CONTEXT → MutationWithAudit. |
| **Hand-rolled** | everything else (`events.rsvp`, `palette.search`, `dashboard.stats`, `members.read`, …) | Inline `if (!this.userId) throw 401` / `validateUserId` → `checkPermission` → body → optional `createLog`. These are reads, narrow validators, or single-shot reads/writes that don't need the standard insert/update/remove audit shape. |

`members.server.ts` is the only file mixing both: its CRUD-shaped paths (`insert/update/remove`) use `runMutation`; its read/list/validator methods are hand-rolled (and several wrap their body in `instrument(...)` from `server/telemetry.ts` to record `denied`/`error`/`ok` outcomes).

### Permission patterns

`checkPermission(userId, module, operation)` (from `server/main.ts`) is the gate. Notable variations:

- **Boolean modules** (`dashboard`, `orbat`, `logs`, `settings`) ignore the `operation` arg — `read` and `update` are identical. This is why `backup.restore` gates on admin (`isOfficerOrAdmin`) instead of `checkPermission('settings','update')`: the latter would not be stronger than read.
- **Synthetic admin-only gate** — `integrity.scan` / `integrity.scanResolve` pass `permissionModule: '__admin_only__'`, a deliberately-unknown module. `checkPermission` short-circuits `true` for admins (`role.roles === true`) before reading the module; every non-admin role falls through the unknown-module branch and is denied.
- **Squad scoping** — member reads merge `getSquadScope(userId)` into the selector so a squad-scoped caller only sees their own squad (see [reference: squad-scoped permissions]). Applies to `members.read/findOne/options/all/groupedOptions/participantNames`, `palette.search` members, and the `members`/`events` publications.
- **Self-or-permission** — `members.attendanceBreakdown` / `members.profileStats` allow viewing your own data freely but require `members.read` (plus squad scope for non-officers) to view another member.

| `user` | members.server.ts:61 | The caller's own member doc, `services` projected out. |

## API surface (custom methods)

| Method | Returns | Permission | Notable logic |
|--------|---------|-----------|----------------|
| `attendances.upsert` | `boolean` | `events.update` | One attendance doc **per event**; each member's status held under a dynamic `[memberId]` key. `upsertAsync({ eventId })` + unique `{ eventId }` index makes it race-safe (#261). `memberId` is hardened against Mongo operator/path chars and structural-field collision via `ID_PATTERN` (`/^[A-Za-z0-9]{17,24}$/`). Status must be one of `-2,-1,0,1,2`. |
| `backup.create` | `BackupData` | `settings.read` | Exports all `BACKUP_COLLECTIONS` + `settings` + `users` (collection fetches raced via `Promise.all`); per-collection failures log `backup.export.error` and yield an empty array. |
| `backup.createQuick` | `BackupData` | `settings.read` | Same as `create` but tags `meta.isSafetyBackup`; used internally as the pre-restore safety snapshot. |
| `backup.restore` | `RestoreResult` | **admin** (`isOfficerOrAdmin`) | SEC-004: validates the **whole** payload before any write (fail-before-write), rejecting `users` docs carrying `services`/`roles`/`profile.roles` or unexpected keys. Creates a safety backup, then wipe-then-insert per collection. Preserves the current user (`{ _id: { $ne: currentUserId } }`) so the caller can't delete themselves mid-restore; swallows duplicate-key on re-insert. |
| `backup.validate` | `{ valid, ... }` | `settings.read` | Shape/appName check only; never throws on bad data (returns `{ valid: false, error }`). |
| `dashboard.stats` | `Record<string, unknown>` | per-module (reads caller's role) | Each stat block is gated by the corresponding `role.<module>` flag. Group-by stats use raw-collection `aggregate` via `aggregateCountByField` / `aggregateCountByArrayField` (the latter `$unwind`s array fields like `specializationIds`). Profile block delegates to `members.profileStats`. |
| `demoData.generate` | `boolean` | `settings` + **dev only** | Throws 403 if `NODE_ENV === 'production'`. `wipeAllCollections()` empties all 20 collections, then `insertDemoData()` reseeds with fixed `_id`s in FK order. **Destructive full reset.** |
| `events.rsvp` | `boolean` (new signed-up state) | auth only | Toggles `this.userId` in/out of the event's `attendees` via `$addToSet` / `$pull`; logs `events.rsvp.added`/`removed`. |
| `events.detail` | enriched event | auth only | Resolves `eventTypeName/Color`, `resolvedHosts`, `resolvedAttendees` (rank-prefixed full names via `resolveNames`), `isSignedUp`. Lookups raced via `Promise.all`. |
| `integrity.preview` | per-id orphan/effect preview | target collection's module, op `delete` | Rejects unknown collections before `runMutation`; previews delete side-effects for one doc. |
| `integrity.previewBulk` | per-id previews + aggregate | target collection's module, op `delete` | Same, batched (max 100 ids); for bulk-delete "N of M blocked" UX. |
| `integrity.scan` | `OrphanRecord[]` | **admin-only** (`__admin_only__`) | Read-only walk of the entire FK graph; reveals every collection's id space, hence admin-only. Audit records `orphanCount`. |
| `integrity.scanResolve` | `OrphanResolution` | **admin-only** | One-off orphan migration (decision O-6). Applies each edge's on-delete primitive (`pull`/`setNull`); `block`/`cascade` orphans → `skipped`. `dryRun: true` counts without mutating. Must run before full-document FK enforcement on a populated DB. |
| `logs.read` | `Log[]` | `logs.read` | — |
| `logs.insert` | id | **server-only** (`this.connection === null`) | Rejects any client call; internal `createLog` is the normal path. |
| `logs.remove` | count | `logs.delete` | — |
| `logs.count` | `number` | `logs.read` | — |
| `members.read` | `User[]` (no `services`) | `members.read` | Squad-scoped; password hashes stripped post-fetch (`stripServicesFromAll`, SEC-001). Wrapped in `instrument`. |
| `members.findOne` | `User \| undefined` | `members.read` | `assertSafeSelector` + squad-scope so a crafted selector can't read outside scope. |
| `members.insert` | id | `members` (create) | `runMutation`; body is `Accounts.createUserAsync` (custom path), so it explicitly calls `validateForeignKeys`. `redact` strips secrets from audit. |
| `members.update` | count | `members` (update) | `runMutation` with `captureBefore` diff snapshot, full-document FK enforcement (`validateForeignKeysForUpdate`), and a `permissionOverride` allowing `canManageSpecializations` holders to update **only** `profile.specializationIds`. Non-officers can't edit members outside their squad. |

## Backup / restore data shapes

```
BackupData   = { version, timestamp, appName: 'community-manager', collections: Record<name, doc[]>, meta }
BackupMeta   = { totalDocuments, collectionCounts: Record<name, number>, isSafetyBackup? }
RestoreResult = { success, restored: Record<name, count>, errors: [{ collection, error }], safetyBackup }
```

`BACKUP_COLLECTIONS` (backup.server.ts:11) is an explicit allow-list; `settings` and `users` are handled separately at the end. The restore allow-list for `users` documents is `['_id','username','profile','createdAt','emails']` with `['services','roles']` (and `profile.roles`) hard-forbidden — the SEC-004 privilege-escalation guard. `backup.create` / `backup.createQuick` / `backup.restore` each carry a `DDPRateLimiter` rule driven by `RATE_LIMITS` from `server/config.ts`.

## Registration → member ("approval") flow

There is **no** `registrations.approve` method. The flow is:

1. The public registration form anonymously calls the generic `registrations.insert` (the only collection with `allowsAnonymous.insert` in `COLLECTION_REGISTRY`).
2. `registrations.validateId` / `validateName` keep the submitted id/name unique across members **and** registrations.
3. An officer reviews the pending registration and "approves" it by creating the real account — `imports/ui/registration/RegistrationExtra.tsx` calls `members.insert` with the chosen username/password/profile, then surfaces `registrations.memberCreated`. The registration doc is managed separately via generic CRUD.

## Demo-data lifecycle

`demoData.generate` (dev only) is a destructive **full reset**, not an append:

1. `wipeAllCollections()` (demoData.server.ts:26) `removeAsync({})`s all 20 collections in parallel.
2. `insertDemoData()` (demoData.server.ts:312) reseeds. Reference collections (roles, squads, ranks, …) go first; members are created via `Accounts.createUserAsync` (account → avatar → profile chain, kept sequential per member, order-preserving across members so `memberIds[i]` aligns with `MEMBERS[i]`); then events, attendances, tasks, a questionnaire + responses, registrations, settings.

Adding a collection means wiring it into **both** `wipeAllCollections()` and `insertDemoData()` (kept alphabetical), or its data silently leaks across regenerations. Rich-text seed fields must use only allow-listed tags (`imports/api/htmlSanitizer/sanitizePolicy.ts`).

## Gotchas

- **New `*.server.ts` must be imported in `server/main.ts`** — otherwise none of its methods/publications register (no error, just a silently-missing method).
- **`settings.public` has no auth** by design (login-screen branding) — never widen its `PUBLIC_SETTING_KEYS` to anything sensitive.
- **`logs.insert` is server-only** (`this.connection === null`); a client can't forge log entries. Use `createLog()` from server code.
- **`attendances.upsert` writes a dynamic document key** — anything bypassing `ID_PATTERN` (or `.`/`$`, or colliding with `eventId`/`_id`) could shadow or rewrite indexed state. The unique `{ eventId }` index (built by `ensureAttendancesUniqueIndex` in `server/main.ts`) is what makes the upsert race-safe.
- **Boolean permission modules** (`dashboard`/`orbat`/`logs`/`settings`) treat `read` and `update` identically — never rely on the operation arg to add privilege there; gate on `isOfficerOrAdmin` when you need a real escalation (as `backup.restore` does).
- **`__admin_only__` is a synthetic module**, not a real one — it only works because `checkPermission` short-circuits for `role.roles === true`. Don't add it to any role.
- **Member password hashes (`services`) must be stripped post-fetch**, never via projection — merging `{ services: 0 }` onto a caller-supplied inclusion projection makes Mongo throw, and omitting it leaks the hash (SEC-001). Every raw-member-returning path calls `stripServices`/`stripServicesFromAll`.
- **`registrations.validate*` and `members.validate*` differ on self-exclusion** — registration validators never self-exclude a member match (members aren't the edit target there), and they run unauthenticated on the public form.
- **`backup.restore` validates the entire payload before any DB write** — a malformed or privilege-smuggling backup aborts with zero mutations. Don't move validation after the wipe.
- **`integrity.scanResolve` must run before full-document FK enforcement** is enabled on a populated DB, or edits to already-orphaned rows start failing.
- **`assertSafeSelector`** must guard any caller-supplied selector that gets persisted and later replayed (`members.saveTaskFilter`, `members.findOne`, `members.participantNames`) so code-execution operators can't be smuggled in.
