# System Documentation

**community-manager** is a Meteor 3.4 + React 18 + Ant Design + MongoDB full-stack
application for managing ArmA III communities — members, events, attendance, tasks,
squads, questionnaires, and the ORBAT org chart, all behind role-based access control.

This directory is the **architecture map**: one doc per subsystem, explaining how the
pieces fit together and why. It complements (does not replace) the field-level reference
in [`../collections.md`](../collections.md), the view inventory in
[`../views-and-forms.md`](../views-and-forms.md), the domain language in
[`../../CONTEXT.md`](../../CONTEXT.md), and the contributor guide in
[`../../CLAUDE.md`](../../CLAUDE.md). Start here when you want the shape of the system;
drill into a subsystem doc for the depth.

## Tech stack

| Layer | Technology |
|-------|------------|
| Language | TypeScript (`strict: true`) |
| UI | React 18, Ant Design |
| Transport / reactivity | Meteor methods + DDP pub/sub |
| Server runtime | Meteor.js 3.4+ on Node 22 |
| Database | MongoDB 7 |
| i18n | Typed in-code translation set (en/de/fr) |
| Rich text | Tiptap (edit) + sanitize-html (server) / DOMPurify (client) |
| Calendar / recurrence | react-big-calendar + rrule |
| Kanban | react-beautiful-dnd |
| ORBAT chart | react-organizational-chart |
| Command palette | fuse.js |
| Unit/integration tests | Mocha (in-process, `node:assert`) |
| End-to-end tests | Playwright (chromium) |
| Build & deploy | Two-stage Docker image, Traefik, GitHub Actions, GHCR |

## Architecture at a glance

```
+-----------------------------------------------------------------+
|  React 18 + Ant Design UI                                       |
|  pathname routing - Section<T> CRUD pages - DrawerStack         |
|  feature views (calendar, kanban, orbat, palette, dashboard)    |
+-----------------------------------------------------------------+
        |  useMethod / Meteor.callAsync        ^  useSubscribe / useFind
        v  (write path)                        |  (reactive read path)
+-----------------------------------------------------------------+
|  Meteor methods  +  DDP publications                            |
+-----------------------------------------------------------------+
        |                                      ^
        v                                      |
+-----------------------------------------------------------------+
|  Generic CRUD engine (server/crud.lib.ts)                       |
|  runMutation pipeline: auth -> permission -> validate ->        |
|                        captureBefore -> body -> audit           |
|  COLLECTION_REGISTRY (permissions, FKs, audit) + RBAC           |
|  referential-integrity (block/setNull/pull/cascade)             |
+-----------------------------------------------------------------+
        |                                      ^
        v                                      |
+-----------------------------------------------------------------+
|  MongoDB — 20 collections (Members = Meteor.users, Events, ...) |
+-----------------------------------------------------------------+
```

A write begins as a client `useMethod` / `Meteor.callAsync`, lands on a Meteor method
(generated by the CRUD factory or hand-written in `server/apis/`), and is funneled through
the single `runMutation` lifecycle — authentication, permission check, input validation,
before-snapshot, the mutation body, and audit logging — all configured from
`COLLECTION_REGISTRY`. The result flows back reactively to every subscribed client via DDP
publications, which is what re-renders `useFind`/`useSubscribe` views. Read the full story
in [Request Lifecycle](request-lifecycle.md) and
[Generic CRUD Engine & Mutation Pipeline](crud-engine.md).

## Relationship to existing docs

`docs/system/` is the **how-it-fits-together** layer. It deliberately points at, rather than
duplicates, the other docs:

- **[`CONTEXT.md`](../../CONTEXT.md)** — the authoritative domain vocabulary and load-bearing
  decisions (MutationWithAudit, CollectionPermissionRegistry, DrawerStack, LocaleSet,
  MethodCall, EntityForm, the Rule of three). System docs reference these terms; CONTEXT.md
  defines them.
- **[`CLAUDE.md`](../../CLAUDE.md)** — the contributor/dev guide: commands, coding conventions,
  the add-a-collection checklist, gotchas. Use it for *how to write code here*; use
  `docs/system/` for *how the system is shaped*.
- **[`docs/collections.md`](../collections.md)** — the field-level schema reference for every
  collection. [Data Model](data-model.md) focuses on relationships and integrity mechanics and
  links out to it for the field lists.
- **[`docs/views-and-forms.md`](../views-and-forms.md)** — the exhaustive index of every
  navigable view, drawer form, and embedded widget. [UI Architecture](ui-architecture.md) and
  [UI Feature Modules](ui-features.md) explain the machinery behind those views.
- **[`docs/deployment.md`](../deployment.md)** — the operational deployment reference (env vars,
  compose notes). [Build, Configuration, Deployment & CI/CD](build-deploy-ci.md) frames the
  build/ship pipeline around it.
- **[`docs/adr/`](../adr/)** — the Architecture Decision Records capturing one-off decisions
  (e.g. rich-text as sanitized HTML). System docs describe the *current* design; ADRs record
  *why* a particular choice was made.
