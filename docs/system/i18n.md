# Internationalization (i18n)

The localization subsystem: one typed translation set (`en`/`de`/`fr`), a generic `t()` translator with compile-time-checked keys and interpolation params, and a React context that persists and auto-detects the active locale.

> **Heads-up for newcomers:** despite the ArmA III / military domain, this app is **not German-first**. The default locale is `en` (`imports/i18n/index.ts:34`), every user-facing string is centralized in one typed table with all three locales filled in, and there is no hardcoded-German-strings-in-components pattern to clean up. The system is a single deep module, not hand-rolled per feature.

## How it works

### Data shape

`translations` is a flat object keyed by dotted strings (e.g. `auth.login`, `validation.maxLength`); each value is a `{ en; de; fr }` row of plain strings. There is **no nesting** — the dotted key is just a string, and the namespace prefix (`auth.`, `backup.`, `events.`, …) is a naming convention, not a structural one. The whole object is sealed with `as const satisfies TranslationSet`, which is what makes the literal key names and per-row strings available to the type system.

```ts
// imports/i18n/translations.ts
export type Locale = 'en' | 'de' | 'fr';
export type TranslationSet = Record<string, Record<Locale, string>>;
export const translations = {
  "auth.login": { en: "Login", de: "Anmelden", fr: "Connexion" },
  // ...607 entries, alphabetically sorted, one per line...
} as const satisfies TranslationSet;
```

Namespaces in use (27): `auth`, `backup`, `briefingTemplates`, `collections`, `columns`, `common`, `dashboard`, `events`, `forms`, `integrity`, `logs`, `members`, `messages`, `modals`, `navigation`, `orbat`, `palette`, `positions`, `questionnaires`, `registrations`, `richText`, `settings`, `specializations`, `squads`, `tasks`, `tour`, `validation`.

### Supported locales & default

| Locale | `name` | `flag` | Notes |
|--------|--------|--------|-------|
| `en` | English | 🇬🇧 | **Default** (`defaultLocale`, `index.ts:34`). The `en` string is the canonical row that param extraction reads from. |
| `de` | Deutsch | 🇩🇪 | |
| `fr` | Français | 🇫🇷 | |

The locale set is closed by `type Locale = 'en' | 'de' | 'fr'` (`translations.ts:6`); the `locales` runtime map (`index.ts:28`) carries the display `name` + `flag` per locale and is what the `LanguageSelector` dropdown and the invariant tests iterate. Adding a fourth locale means extending both the `Locale` union and the `locales` map (see *Adding a locale*).

### Reading a string in a component

A component calls the hook, then the translator:

```tsx
import { useTranslation } from '../../i18n/LanguageContext';

function Foo() {
  const { t } = useTranslation();
  return <Button>{t('common.create')}</Button>;          // param-less key
}
```

For keys whose value contains `{{placeholder}}`s, TypeScript **requires** a typed params object as the second argument:

```tsx
t('questionnaires.answeredOf', { answered, count });       // "{{answered}}/{{count}} answered"
t('validation.maxLength', { max: 50 });                    // "Maximum {{max}} characters"
```

`Section<T>` column factories receive `t` as a parameter rather than calling the hook themselves: `const getEntityColumns: ColumnsFactory<Entity> = (handleEdit, handleDelete, permissions, t) => [...]`. There are **~750 `t('…')` call sites** across `imports/ui/` (`.ts` + `.tsx`).

`useLanguage()` is the fuller hook (`{ language, setLanguage, t, locales }`); only three sites need it (`LanguageSelector`, and code that reads/sets the active language). Everyone else uses `useTranslation()` for just `{ t }`.

### Interpolation

Placeholders use `{{name}}` syntax. **15 keys** take params today. At render time `getTranslation()` (`index.ts:44`) looks up the row, then `interpolate()` (`index.ts:38`) replaces each `{{name}}` against the params object. A missing param is left as the literal `{{name}}` rather than throwing.

```ts
const PLACEHOLDER_PATTERN = /\{\{(\w+)\}\}/g; // index.ts:36 and extract-params.ts:12
```

The complete set of param-taking keys (audit them when changing placeholder names):

| `integrity.usageEntryWithMore` | uses `{{count}}`, `{{label}}`, `{{names}}`, `{{more}}` |

### Type-level guarantees

The leverage of this module is what is **structurally impossible**. All of the following are compile errors, not runtime fallbacks:

| Invariant | Mechanism | Where |
|-----------|-----------|-------|
| Typo on the call site (`t('comon.create')`) | `LocaleKey = keyof typeof translations` | `index.ts:7` |
| Missing translation for a locale | row shape `Record<Locale, string>` via `satisfies TranslationSet` — a partial row fails to satisfy | `translations.ts:618` |
| Missing / extra interpolation param | `ParamArgs<K>` makes the params arg required iff `ExtractParams<translations[K]['en']>` is non-empty, and its keys must match | `index.ts:9`, `extract-params.ts:6` |
| Passing params to a param-less key | `ParamArgs<K>` resolves to `[]` (no second arg) when the `en` string has no `{{…}}` | `index.ts:9` |
| Cross-locale structural drift | there is no nesting; the structure *is* the type | n/a |

`ParamArgs<K>` is the keystone:

```ts
// index.ts:9
export type ParamArgs<K extends LocaleKey> =
  keyof ExtractParams<(typeof translations)[K]['en']> extends never
    ? []                                                  // no params -> t(key)
    : [params: ExtractParams<(typeof translations)[K]['en']>]; // params required
```

`ExtractParams<S>` (`extract-params.ts:6`) is a mapped type over `ExtractParamNames<S>`, a recursive template-literal type (`S extends \`${string}{{${infer P}}}${infer Rest}\``) that walks the string and unions every placeholder name, each typed `string | number`.

`ParameterlessLocaleKey` (`index.ts:19`) is the subset of `LocaleKey` whose `ParamArgs` is `[]`. Static config that stores a label key (so a caller can do `t(config.labelKey)` with no params argument) types the field as `ParameterlessLocaleKey` — consumed by `imports/ui/palette/palette.items.ts` and `imports/ui/hooks/useEntityForm.ts`.

### Runtime flow

| Symbol | Role |
|--------|------|
| `LanguageProvider` | Holds `language: Locale` state; mounted around `<App />` in `ReactTarget.tsx`. |
| `useLanguage()` | Returns the full context `{ language, setLanguage, t, locales }`; throws if used outside the provider. |
| `useTranslation()` | Convenience wrapper returning just `{ t }`. |
| `t(key, ...args)` | The generic translator; calls `getTranslation(key, language, ...args)`. |
| `getTranslation(key, locale, ...args)` | Pure lookup + interpolate; usable outside React (it takes an explicit `locale`). |
| `setLanguage(lang)` | Validates `lang in locales`, sets state, writes localStorage, sets `<html lang>`. |
| `LanguageSelector` | Header dropdown; maps `locales` to `{ value, label: flag+name }` options, calls `setLanguage`. |

Initial-locale resolution in `LanguageProvider` (`LanguageContext.tsx:16`), in order:

1. `localStorage['community-manager-language']` if present and a known locale.
2. `navigator.language` primary subtag (e.g. `de-AT` → `de`) if a known locale.
3. `defaultLocale` (`'en'`).

`setLanguage` persists the choice to localStorage (`STORAGE_KEY = 'community-manager-language'`) and sets `document.documentElement.lang`; a `useEffect` also keeps `<html lang>` in sync with `language`.

The provider's `t` is built with **`useMemo`, not `useCallback`** (`LanguageContext.tsx:48`) — deliberately, because `useCallback`'s inference erases the function's `<K extends LocaleKey>` generic down to its constraint, which would break per-key param typing at every call site.

### Adding a translation string

1. Add **one line** to `imports/i18n/translations.ts` with all three locales filled in:
   ```
   "namespace.newKey": { en: "...", de: "...", fr: "..." },
   ```
2. Keep the file **alphabetically sorted by dotted key** and one entry per line. The file is prettier-excluded (`.prettierignore`), so formatting is manual and the dense layout is intentional for diff-friendliness.
3. Use the new key with `const { t } = useTranslation(); t('namespace.newKey')`. If the value contains `{{param}}` placeholders, TS will require `t('namespace.newKey', { param: ... })`.
4. Placeholder names must match `/^\w+$/`. The same set of `{{params}}` must appear in **all three** locale strings (see invariant tests).
5. If the key lives under `collections.*`, `dashboard.stats.*`, or `dashboard.profileLabels.*`, also add it to the corresponding dynamic-key map (see *Invariant tests*), or the completeness test fails.

### Adding a locale

1. Extend the `Locale` union in `translations.ts:6` (e.g. `'en' | 'de' | 'fr' | 'es'`). This immediately turns **every** `translations` row into a compile error until its new-locale string is filled in — `satisfies TranslationSet` enforces the full row.
2. Add the locale to the `locales` map (`index.ts:28`) with `{ name, flag }`. The `LanguageSelector` dropdown and all invariant tests derive their locale list from this map, so they pick up the new language automatically.
3. Fill in the new-locale string for all 607 keys.

## Invariant tests

Wired through `tests/main.ts:20-21` and run by `npm test`:

| Test (`tests/server/`) | Guards |
|------------------------|--------|
| `i18n.extractParams.test.ts` | `extractParams()` returns only `\w+` names (dedup, ignores `{name}`, `{{ }}`, `{{!@#}}`, `{{}}`); `assertValidPlaceholders()` throws on hyphen/space/empty placeholder interiors. Also includes type-level `Expect<Equal<…>>` assertions for `ExtractParams<S>`. |
| `i18n.invariants.test.ts` → cross-locale param invariants | Every key has the **same** `{{params}}` set in `de`/`fr` as in `en` (catches a translator dropping or renaming a placeholder). |
| `i18n.invariants.test.ts` → placeholder-syntax invariants | Every value in **every** locale uses only `\w+` placeholder names. |
| `i18n.invariants.test.ts` → dynamic-key-map completeness | `COLLECTION_LABEL_KEYS` (`imports/ui/backup/Backup.tsx:19`), `STATS_LABEL_KEYS` (`imports/ui/dashboard/Dashboard.tsx:13`) and `PROFILE_LABEL_KEYS` (`Dashboard.tsx:27`) cover **every** `collections.*` / `dashboard.stats.*` / `dashboard.profileLabels.*` key — so a new key under those prefixes can't silently render its raw data string. |

The locale lists in `i18n.invariants.test.ts` are **derived from the runtime `locales` object** (`Object.keys(locales)`), so adding a fourth language to `index.ts` automatically extends every invariant test.

## Gotchas

- **Type/runtime placeholder asymmetry.** `ExtractParams<S>`'s `${infer P}` matches *any* string between `{{` and `}}` (hyphens, spaces, empty), but the runtime `extractParams()` / `interpolate()` only match `\w+`. A placeholder like `{{user-name}}` would type-check yet be ignored at render time. `assertValidPlaceholders()` exists to fence this, and the invariant tests run it across the whole set — so the trap is caught in CI, not by the type system. See the warning comment atop `extract-params.ts`.
- **Missing param renders literally, doesn't throw.** `interpolate()` leaves an unsupplied `{{name}}` in the output rather than erroring. The compile-time `ParamArgs` check is the real guard; don't rely on runtime to surface a missing param.
- **Use `useMemo` (not `useCallback`) for any wrapped `t`.** `useCallback` collapses the generic signature into its constraint and loses per-key param typing — the provider does this deliberately (`LanguageContext.tsx:46-48`).
- **`useLanguage()` / `useTranslation()` only inside `LanguageProvider`.** Calling outside throws `'useLanguage must be used within a LanguageProvider'`. The provider wraps `<App />` in `ReactTarget.tsx`, so app code is fine; isolated tests/stories that render a component bare are not — the server-side invariant tests sidestep this by importing `translations`/`getTranslation` directly (no React).
- **Don't reformat `translations.ts`.** It is prettier-excluded on purpose; running a formatter or re-sorting non-alphabetically produces a noisy, hard-to-review diff. The one-entry-per-line, alphabetical layout is what keeps translation diffs reviewable.
- **New `collections.*` / `dashboard.stats.*` / `dashboard.profileLabels.*` keys need a map entry.** These render dynamic data (a collection name, a stat label, a profile-field label) through `COLLECTION_LABEL_KEYS` / `STATS_LABEL_KEYS` / `PROFILE_LABEL_KEYS`; omitting the map entry fails the completeness test (and would otherwise render a raw key/data string).
- **Param parity across locales is enforced.** Adding `{{count}}` to the `en` string but not `de`/`fr` (or vice versa) fails the cross-locale invariant test. Keep the placeholder set identical in all three strings.
- **`en` is the canonical row for param extraction.** `ParamArgs<K>` and the cross-locale test both derive the *expected* placeholder set from `translations[K]['en']`. If you intend a key to take params, the `en` value must contain them.
- **JS/TS purity here.** Unlike some other corners of the app, the i18n module is fully TypeScript with `strict: true`; there is no ad-hoc/untyped fallback path. The depth is entirely in the type layer, so a key/param mistake surfaces at `tsc`, not at runtime.
